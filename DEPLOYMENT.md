## Response security headers

The Pages static output uses `frontend/_headers`. Function-generated responses are hardened through `functions/_shared/http.js` and `functions/api/_middleware.js`; Pages `_headers` rules do not apply to responses generated by Pages Functions. See the [Cloudflare Pages headers documentation](https://developers.cloudflare.com/pages/configuration/headers/).

| Header | Policy |
|---|---|
| `X-Frame-Options` | `DENY` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `no-referrer` |
| `Cache-Control` | `no-store, no-cache, must-revalidate` |
| `Permissions-Policy` | `geolocation=(), microphone=(), camera=()` |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains; preload` |

The no-store rule applies to static assets as well as application pages. This prioritizes confidentiality for an HR application over browser asset caching.

The following bindings are configured for the production Pages Functions environment:

| Binding | Resource | Purpose |
|---|---|---|
| `DB` | D1 `jelhr-system-db` (`65b599fb-e45d-4f92-8588-d353df0e1cb8`) | Tenant, employee, recruitment, auth, audit and workflow records |
| `FILES` | R2 `jelhr-files` (APAC) | Résumés, employee documents and uploaded files |
| `AI` | Workers AI | HR assistant, screening and document conversion |
| `VECTORIZE` | Vectorize `jelhr-knowledge` (768 dimensions, cosine) | Optional semantic retrieval, organization namespace isolation |
| `MAILER` | Worker service `jelhr-mailer` | Internal SES SMTP delivery |
| `TURNSTILE_SECRET_KEY` | Encrypted Pages secret | Server-side Cloudflare Siteverify for login and optional careers challenges |

The login page obtains its public widget site key from `GET /api/auth/config`, which reads the production Pages variable `TURNSTILE_SITE_KEY`. The login API sends the submitted token and client IP directly to Cloudflare Siteverify using the encrypted `TURNSTILE_SECRET_KEY`. It fails closed unless Siteverify returns `success: true`, the hostname matches the request hostname, and the action is `login`. The careers application endpoint similarly checks the `careers_apply` action when Turnstile is enabled.

Production Pages configuration must therefore include:

- `TURNSTILE_SITE_KEY` — public Turnstile site key, configured as a Pages production variable (not a secret).
- `TURNSTILE_SECRET_KEY` — encrypted Pages secret. Required for login Turnstile verification. Never put this value in frontend code, GitHub, or a plaintext Pages variable.

Register the production Pages hostname (`jelhr-system-213.pages.dev`) and any production custom hostname actually used by the login page in the Turnstile widget's allowed domains. Do not add localhost to the production hostname allowlist. Keep the service binding and site key configured in the production environment, not only preview environments.

## Email and Secrets Store

Pages Functions cannot consume Cloudflare Secrets Store bindings directly. JelHR therefore uses an internal Worker service binding:

1. Pages Functions call `env.MAILER.fetch()`.
2. The `jelhr-mailer` Worker accepts only its internal `POST /send` contract and is not intended to have a public route.
3. The Worker reads the shared Operava Secrets Store entries `SES_SMTP_HOST`, `SES_SMTP_PORT`, `SES_SMTP_USERNAME`, and `SES_SMTP_PASSWORD`.
4. The Worker sends through the existing AWS SES SMTP endpoint in `ap-southeast-2`.

The SMTP values are write-only Secrets Store values. They are not copied into GitHub, Wrangler, or Pages variables. The mailer Worker binds to the existing secret names in the Operava account's default Secrets Store.

Cloudflare configuration was checked after the credential update. The `jelhr-mailer` Worker has four `secrets_store_secret` bindings attached: `SES_SMTP_HOST`, `SES_SMTP_PORT`, `SES_SMTP_USERNAME`, and `SES_SMTP_PASSWORD`. The shared store also lists `SES_SMTP_REGION`; it is not currently bound to the Worker. Secret values are masked and are intentionally not included in GitHub documentation.

The Pages project has encrypted secrets:

- `JELHR_JWT_SECRET` — session signing and OTP HMAC key material.
- `JELHR_ENCRYPTION_KEY` — AES-GCM key material for encrypted SSO/TOTP values.

Their values are intentionally not documented or returned by Cloudflare.

### Platform super-admin bootstrap status

The Pages production configuration lists encrypted secret entries for `JELHR_SUPERADMIN_EMAIL` and `JELHR_SUPERADMIN_PASSWORD`. Their values are write-only and cannot be verified from configuration metadata. The latest live health response still reports `platformAdmin: false`, so the platform administration plane must be treated as not initialized. Before using `/platform.html`, verify that both values are non-empty, redeploy, and confirm the health endpoint reports `platformAdmin: true`:

- `JELHR_SUPERADMIN_EMAIL`
- `JELHR_SUPERADMIN_PASSWORD` (minimum 16 characters)

Optional: `JELHR_SUPERADMIN_TOTP_SECRET`, `JELHR_WEBAUTHN_RP_ID`, `JELHR_WEBAUTHN_ORIGINS`, `AI_API_BASE`, `AI_API_KEY`, `ANTHROPIC_API_KEY`. `TURNSTILE_SITE_KEY` is public; `TURNSTILE_SECRET_KEY` must be encrypted and present for login.

Do not reuse credentials from another Operava application. After setting these secrets, trigger a production redeployment and verify `platformAdmin: true` from the health endpoint.

## Database migration and preservation

Migrations `0001_init.sql` through `0004_recruitment_ai_auth.sql` have been applied to the Operava Business D1 database. The target `d1_migrations` table records all four migrations.

The previous `jelhr-system` Pages project and original D1 database in Projects - Works were left intact. The old Pages project's GitHub source connection was disconnected so the same repository could be connected to Operava Business. Its existing D1 database was not deleted or modified.

A read-only data audit of the original application tables found zero organization, user, employee, applicant and operational records. The new production database therefore has the complete v0.4 schema and no application rows to copy. The original database remains available as a preservation copy.

Do not delete the legacy project or its D1 database until the new production environment has been accepted.
